# Wardryx 1.0.0

The policy decision point of the TAIPANBOX stack: `POST /v1/decide` answers
`allow`, `deny` or `hold` for an agent's next action, every decision is
audited to the shared event bus, and a hold resolves through a stateless,
signed approval token an admin mints.

## What 1.0 promises

`compat/1.0.json`, rendered as `COMPATIBILITY.md` and held by
`scripts/compat-surface.sh` on every push: the nine routes, the `/v1/decide`
request and response fields, the three decision words, the eleven policy
fields, the five subcommands, the eleven `WARDRYX_*` variables and the eight
event types. A frozen name is not removed or renamed within this major. Support
line: the newest minor gets every fix; the previous minor gets security-relevant
fixes for 90 days after the newer one is tagged.

## Proven, by the 1.0 proving run (estate-gates `PROVEN.md`, section "The 1.0 proving run")

- **RUN-8, R2 on GCP and AWS.** The 34-request concurrent burst with per-agent
  differentiated rights against the shipped policy: 34 of 34 decisions exactly
  right. 3000 decisions at 16 to 256 concurrent callers: 21 000 to 43 000
  decisions per second from one pod, p99 2.4 to 44 ms, no 5xx, no cliff; every
  decision on the bus at about 390 bytes each.
- **POL-2, R2.** `approval-required` end to end: hold, admin grant, the token
  presented twice. Under 0.1.0's default the second presentation was allowed
  again; under `WARDRYX_APPROVAL_SINGLE_USE=true`, flipped live and back, it
  was a fresh `hold`. Both behaviours of invariant 5 recorded; 1.0 ships the
  second as its default.
- **FAIL-4, R2 on GCP and AWS.** A freeze written through the admin API into
  the Postgres store survives a restart of the policy plane: `deny` before,
  `deny` after.
- **FAIL-2, R1.** Wardryx killed under a running gateway and scopyx: the
  gateway in fail-closed mode refuses every call while the decider is down;
  nothing forbidden was ever allowed.
- **POL-3, R1.** Scopyx's egress gates in order against this plane's decisions.
- **INS-2, INS-3, R1.** Installed and serving by the stack-single one-liner on
  x86_64 and on arm64; INS-5, R2, on five-node clusters on GCP and AWS with
  the Postgres policy store.

## Upgrade note, 0.1.0 to 1.0.0

Policies written through `PUT /v1/policies/{id}` live in Postgres
(`WARDRYX_DB`) and survive the upgrade unchanged; file-loaded policies
(`WARDRYX_POLICY`) are re-read at start. Every policy set that decided anything
is in the archive (`WARDRYX_POLICY_ARCHIVE`) by version, and `wardryx replay`
reproduces a recorded decision against it. The approval store is Postgres too;
a token minted under 0.1.0 verifies under 1.0.0 with the same
`WARDRYX_APPROVAL_SECRET`.

The one behaviour decision of this release is the approval token's default,
which is configuration and not wire: see the line below, and set
`WARDRYX_APPROVAL_SINGLE_USE` explicitly if the default does not suit you.

**Approval tokens are single-use by default from 1.0.** Under 0.1.0 a granted
token stayed valid for every `/v1/decide` call within its TTL; from 1.0 the
first redemption is the only one, and a second presentation returns a fresh
hold (`approval_token was already redeemed once`). Set
`WARDRYX_APPROVAL_SINGLE_USE=false` to keep the 0.1.0 behaviour; an unset or
unparsable value is single-use. Agents that retried a call by re-presenting the
same token now get a hold and need a new approval, which is the point. With
`-db` unset the redemption set lives in one process and `serve` says so at
start; the stack's launchers run this plane on Postgres.

## Not in this release, said plainly

- The console's WebAuthn passkey ceremony for approvals was not exercised in
  the proving run (the API half was; the ceremony is the operator's).
- `UPG-2` (a 0.1.0 store upgraded in place to this release, `replay` reproducing
  a recorded decision) runs against this image once it exists and is recorded
  in `PROVEN.md` afterwards.
- OTLP span export and replay's candidate-policy report are experimental
  (`compat/1.0.json`).
