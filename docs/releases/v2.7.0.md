# Wardryx 2.7.0

2.7.0 shows the person who decides a held tool call what the call's arguments are. The preview is built from the exact bytes the grant is bound to, never from anything a model wrote about them, with secrets and personal data hidden by fixed rules. It is sealed to the console's key, and the decision records the preview the person was shown (CLAUDE.md invariant 51).

It is a minor release, and it does nothing until a preview key is set. **With `WARDRYX_PREVIEW_RECIPIENT` unset, every decision, reason and `policy_version` is what 2.6.2 gives**. A hold with a tool call records its preview as `off`, and a console that sends a version 1 approver statement decides as before. The one step every deployment with a database goes through is the new table below, created at start.

Tag: `v2.7.0`. The image is `ghcr.io/taipanbox/wardryx:v2.7.0`. There is no moving tag (no `latest`, no `main`).

## Upgrade

- **No preview key.** Replace the 2.6.2 image with 2.7.0. Holds, grants, denials and replay work as they did. The approval context and `approval_requested` gain the member `preview: off` on a hold that carries a tool call, and `approval_granted` and `approval_denied` gain `preview`, with `preview_state` where the hold recorded one. Nothing has to read them.
- **`WARDRYX_DB` set: the schema step.** A new table, `approval_previews`, is created at start the way the rest of the schema is, so there is no manual step. It holds ciphertext only, one row per sealed hold. Existing tables are not changed.
- **Turning the preview on.** Do it after the upgrade, as a change of its own, in this order:
  1. Run a console that reads previews (genaryx with `GENARYX_PREVIEW_KEY_FILE`, from fb5e036 on) and generate its key: `genaryx-web preview-key -out <file>` writes the private key to a file only its owner can read and prints the recipient. `wardryx preview-key -out <file>` does the same. The private key belongs to the console alone, and wardryx never reads it.
  2. Set `WARDRYX_PREVIEW_RECIPIENT` to the printed `hpke:...` value and restart wardryx. `WARDRYX_PREVIEW_TTL` is optional: unset is 24 hours.
  3. Only then add `require_preview: true` to the policies whose grants must be read first, if any, and restart.

  **The console moves before the key is set.** A console that sends version 1 statements cannot decide a sealed hold at all: wardryx refuses a version 1 statement on a hold whose preview was sealed, with `403 approver_statement_mismatch`, grant or deny, and the hold stays pending. A decision made by a key rather than a person is not refused for this, and is recorded as `unseen`, except a grant under `require_preview`.
- **Several instances.** Move every instance to 2.7.0 before the key is set on any of them. A 2.6.2 instance refuses a version 2 statement, and a policy file with `require_preview`.
- **`WARDRYX_PREVIEW_RECIPIENT`** names ML-KEM-768 with X25519 (`647a`, the default `preview-key` writes) or X25519 (`0020`). Anything else, or a value that does not parse, refuses to start. **`WARDRYX_PREVIEW_TTL`** is a Go duration from `1m` to `168h`, or `serve` refuses to start.

## Rollback

**Take `require_preview` out of the policy file first, then move the console and wardryx back together.** A wardryx older than this one refuses `require_preview` at load, and refuses a version 2 approver statement, which a console that reads previews sends for every hold that records a preview, `off` included. The steps:

1. Remove every `require_preview` from the policy file and restart 2.7.0 on it.
2. Decide or let lapse the holds 2.7.0 wrote, or accept that a person cannot decide them from either console after the rollback: the new console sends a version 2 statement for them, which 2.6.2 refuses, and the old console has no preview to show.
3. Run the 2.6.2 image and the console you ran before.

The `approval_previews` table can stay: 2.6.2 neither reads nor writes it, and it holds ciphertext only. Its rows stop expiring, since 2.6.2 does not purge them; drop the table if you want them gone. 2.7.0 creates it again at its next start.

## Added

- **The preview.** When a hold carries a `tool_call` with arguments, wardryx builds a preview from `tool_call.arguments` as received: the bytes `arguments_sha256` hashes. It is a tree of typed nodes (object, array, string, number as written, bool, null, hidden, vault handle, blob, elided), never text or markup, in the order the bytes hold them, with repeated keys shown and flagged.
- **Ruleset `r1`, deterministic.** A member whose key names a credential is hidden whole. Inside every string and key: the secret kinds the TokenFuse broker's DLP scans for, an email address, a card number that passes Luhn, an IBAN that passes mod-97, an international phone number, and a run of 40 or more base64 characters at 4.5 bits of entropy a character or more. A hidden value carries its rule and JSON type, never a length or a hash. A `{{secret:NAME}}` vault handle is shown by name. Encoded bytes are shown as their decoded size, type and sha-256, never decoded. Limits: 512 characters a string (the first 256 shown), depth 8, 50 items an array, 100 members an object, 16 KiB the whole. Control, bidirectional, invisible and mixed-script characters are flagged. The same bytes always give the same preview and the same digest, `pvd`.
- **Sealed and kept briefly.** The preview is sealed with HPKE (RFC 9180; HKDF-SHA256, ChaCha20-Poly1305) to the console's key, bound to the org, the call's digest, the preview's digest and the ruleset. wardryx keeps the ciphertext until the hold is decided (deleted in the same transaction as the decision) or the TTL runs out (purged every minute, never served after it).
- **`GET /v1/approvals/{id}/preview`.** For an admin key of the hold's org: the ciphertext with its suite, `pvd`, `ruleset` and `expires_at`, under `Cache-Control: no-store`. A hold of another org, or one with no preview recorded, is a `404`. A hold whose preview is not sealed answers its state. A sealed one that was decided, expired or not kept is a `410`. An admin key reads nothing it could not read before, since only the console's private key opens the ciphertext.
- **Approver statement version 2.** It carries `tcd`, the call's digest, and `pvd`, the preview's digest, each a digest or `none`. wardryx refuses with `403 approver_statement_mismatch`, before anything is decided, a statement whose `tcd` is not the hold's call, whose `pvd` is not the hold's sealed preview, or that names a preview where none was sealed. A denial may name no preview on a sealed hold (#144): refusing a call opens nothing, and it is recorded as unseen. Version 1 statements are still accepted on every hold with no sealed preview.
- **`require_preview`**, a policy field set only in the policy file. A grant of a call it holds then needs a person whose statement names the sealed preview, or a call that had no arguments. Anything else is `403 preview_required`. A denial is always allowed. `PUT /v1/policies/{id}` refuses the key with a `400`, for the reason it refuses `when_no_grant`. A file without it keeps its `policy_version`.
- **The record says what the person saw.** An approval's context and `approval_requested` carry `preview` (`sealed`, `truncated`, `no_arguments`, `off` or `unavailable`) and, for a sealed one, `pvd` and `ruleset`. `approval_granted` and `approval_denied` carry `preview` as `seen`, `unseen` or `no_call`, with `preview_state` and, for a version 2 statement, `preview_digest` and `tool_call_digest`. Never the preview, never the arguments: `scripts/preview-never-in-record.sh` holds that.
- **`wardryx preview-key -out <file>`** writes a new private preview key at mode 0400, refuses to overwrite a file, and prints the recipient.

## Changed

- **A decision on a hold is one transaction with its preview's deletion** on Postgres, so a decided hold never leaves a readable ciphertext behind.
- **`agent-stack-go` v2.0.3** (#145), the shared library rebuilt on Go 1.27.4. No behaviour change in wardryx.

The preview changes no verdict. A hold with no preview is held, granted and replayed as before.

## Limits

- The preview is what the enforcement point sent. A call marked `arguments_truncated` has no preview (`truncated`), and its grant binds only name, target and the flag, as before.
- Hiding is by fixed rules. A secret in a shape `r1` does not know is shown. The rules err toward hiding (a credential word anywhere in a key, high entropy), so a person sometimes sees `hidden` where a harmless value was.
- The console is trusted to show what it opened. wardryx checks that the statement names the preview it sealed, not that a person read it.
- The approver statement does not make a decision by a key into a person's decision. Without `WARDRYX_APPROVER_JWKS`, every decision is a key's and is recorded `unseen`.
