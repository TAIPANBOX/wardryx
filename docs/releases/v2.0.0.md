# Wardryx 2.0.0

2.0.0 binds a decision request to the key that makes it, and it changes what an
existing deployment has to do. Three things now refuse calls that 1.5.0 let
through: a `viewer` key can no longer ask for decisions, a key with an agent
list speaks only for those agents, and an org admin's policies belong to that
org. Read **Breaking** and **Migration** before upgrading. Everything else is
additive, and no name `compat/1.0.json` freezes is removed or renamed.

## Breaking

- **A `viewer` key is refused on `POST /v1/decide` and `POST /v1/filter-tools`.**
  The refusal is a `403` that echoes nothing the request carried, for every
  agent. On 1.5.0 a viewer key could ask for decisions. A `viewer` key still
  reads `GET /v1/approvals` and `GET /v1/status`.
- **A key with an agent list speaks only for the agents it lists.** The
  `[:agents]` segment of a `WARDRYX_KEYS` entry is enforced for every role. A
  request naming an agent outside it is a `403` with no decision, no hold, no
  approval token read or spent, and one `agent_assertion_refused` event. An
  unlisted `viewer` speaks for no agent. An unlisted `pep` or `admin` speaks for
  any agent of its own org when every key belongs to one org. In a deployment
  with more than one org it speaks for no agent until its entry lists them.
- **The approver is the key, not the text a caller sent.** `decided_by` on an
  approval, in `GET /v1/approvals` and in the `approval_granted` and
  `approval_denied` events, is `key:` followed by the first 16 hex characters of
  SHA-256 over the deciding bearer key. The text a caller sends is kept as
  `decided_by_label`. Anything that read `decided_by` as a person's name now
  reads a key fingerprint.
- **An org admin's policies belong to its org.** A `PUT /v1/policies/{id}` from
  an org admin is stored under that admin's org, and a body naming another org
  is a `403`. An org admin cannot replace or delete a policy that belongs to
  another org or applies across orgs (`403`), and cannot read one (`404`). A
  policy with an org governs only the decisions that org's keys ask for.
- **An approval with no org is decided and listed only by a principal allowed
  across orgs.** That is a `cross-org-admin` key. In a deployment with one org,
  its admin still decides it.

## Migration

1. **Enforcement points: change the role from `viewer` to `pep`.** Every
   `WARDRYX_KEYS` entry that TokenFuse's gateway or broker, scopyx or another
   enforcement point uses moves from `key:org:viewer` to `key:org:pep`. Keys that
   already carry `admin` or `pep` keep working in a one-org deployment. Change the
   entry before the new build takes traffic: otherwise every governed call that
   key makes is refused, and TokenFuse with failmode closed denies it.
2. **Multi-org deployments: list the agents on every `pep` and `admin` key that
   asks for decisions.** The agent patterns follow the role, separated by `|`, in
   a policy `target`'s glob syntax, for example
   `gw-secret:acme:pep:agent://acme.example/*|agent://ops.acme.example/runner`.
   `serve` prints, at start, each key that speaks for no agent, by fingerprint.
3. **Multi-org deployments: policies and approvals that cross orgs need a
   `cross-org-admin` key.** Write a policy with no `org` through such a key, and
   decide an approval with no org through one too.
4. **Stored policies without an org keep applying across orgs.** A policy an org
   admin writes from 2.0.0 on is stamped with that admin's org. To keep a policy
   cross-org, write it through a `cross-org-admin` key.
5. **Readers of `decided_by`: read `decided_by_label` for the text.** A console or
   export that shows `decided_by` shows the `key:` fingerprint until it reads the
   label. To find the key behind a fingerprint, run
   `printf %s "$KEY" | shasum -a 256 | cut -c1-16`.

## Added

- Roles `pep` (an enforcement point: `/v1/decide`, `/v1/filter-tools`, and what
  `viewer` reads) and `cross-org-admin` (every endpoint, for every org).
- The `agent_assertion_refused` event, emitted under `source: wardryx` when a
  request names an agent its key does not speak for.
- The policy field `org`. A policy without one applies across orgs and keeps its
  `PolicyVersion` byte for byte.
- Every decision event records the org that asked, and replay feeds it back to
  the PDP.
- `key_fp` on `policy_updated`: the first 16 hex characters of SHA-256 over the
  bearer key that made the write, so an operator can tell keys of one org apart.
  The raw key is never stored, logged or emitted.
- `decided_by_label` on an approval: the text a caller sent, at most 256 bytes,
  with no control or bidi override character. A value that breaks this is a `400`
  that does not echo it. Stored in a new nullable column, `approvals.decided_by_label`,
  added with `ADD COLUMN IF NOT EXISTS`.

## Changed

- `POST /v1/filter-tools` is bound to the key that asks, as `POST /v1/decide` is.
- A refused request never reaches `Decide`, so the decision rules, the decision
  words and `chain_proven` are unchanged.
- `agent-stack-go` is pinned at v1.3.0 (1.5.0 pinned v1.1.0). v1.2.0 takes an
  exclusive lock per chained write; v1.3.0 takes the same lock for plain writers.
  No exported identifier moved, and this repository's writers are chained, so
  their behaviour is unchanged.

## Security fixes, by what they close

- A caller could name, in `/v1/decide` or `/v1/filter-tools`, an agent its key was
  not issued for and get a decision, a hold or a spent approval for that agent.
  The agent a request is about is now bound to the key (invariant 36).
- An approval recorded the free text a caller sent as the person who decided it.
  The approver is now the deciding key (invariant 37).
- A policy carried no org, so an org admin's policy could govern another org's
  agents. Policies now carry an org, an org admin writes only its own, and a
  decision is governed only by the policies of its org or those that apply across
  orgs (invariant 38).
- A `decided_by` label carrying control characters or bidi overrides is refused
  with a `400` that does not echo it.

## Upgrade notes

- No new environment variable and no new route. `compat/1.0.json` names no frozen
  name removed or renamed; `scripts/compat-surface.sh` holds the surface.
- **Rollback.** A 1.5.0 build reads a `pep` or `cross-org-admin` role as unknown:
  it warns once per such entry at start, lets a `pep` key decide, and refuses both
  roles on admin routes. It ignores the agent list, so a key that listed agents
  speaks for every agent again. Remove agent lists and org-scoped policies before
  rolling back: a 1.5.0 build reads a stored policy with a decoder that drops
  `org`, which widens that policy to every org, the same way 1.5.0 read
  `allow_models` in its notes. The `decided_by_label` column is ignored by older
  builds.

## Documentation and tests

- 511 test functions, up from 472 in 1.5.0. Three feature files bind their
  scenarios to named tests: `features/agent-bound-to-its-key.feature`,
  `features/approver-is-the-key.feature` and `features/policy-belongs-to-an-org.feature`.
- CLAUDE.md invariants 36 to 38, checked by `scripts/agent-is-bound-to-its-key.sh`,
  which is one of the gates, with six cases in `scripts/gates-have-teeth.sh`.
- The README sections "Which agents a key speaks for", "Who decided is the key"
  and "A policy belongs to an org" describe the rules above.

## Not proven: where it says nothing

- The Postgres paths (the `decided_by_label` column, the migration on an existing
  database, and the stored-policy org) run in CI's integration job, not in the
  checks made for this release.
- No launcher was run against this build, and no live enforcement point has yet
  received a `403` from it.
- The agent binding checks a request against the key. It does not verify the
  agent's identity: an unlisted `pep` key in a one-org deployment speaks for any
  agent id, and the enforcement point's own identity check is what makes that
  agent real.
- Fingerprints name keys, not people. Approvals decided before 2.0.0 keep the
  text in `decided_by`.
- `wardryx check` asks in no org, so it applies only policies that apply across
  orgs.
