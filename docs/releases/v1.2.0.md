# Wardryx 1.2.0

A typed risk signal can hold a call, and an approval is now bound to the exact
tool call a person read. Both are additive and optional: a deployment that
sends neither `signals` nor `tool_call` decides and approves exactly as it did
under 1.1.3. This release was approved by the owner.

## Added

- **Typed risk signals on `/v1/decide` (wardryx#81, invariant 27).** The
  request takes an optional `signals` list (`name`, `value`, `probability`,
  `source`, `answer_id`, at most 16) and an optional `tool_call` (`name`,
  `arguments` as raw JSON up to 12 KiB, `target`, `arguments_truncated`).
  Malformed input is a 400 that echoes nothing, and a tool call that says
  `arguments_truncated` while also sending arguments is a 400.
- **Policy rule `hold_if_signal {name, values, min_probability}`.** It runs
  last, after every deny rule and the cost gate, and it can turn an allow into
  a hold and change nothing else: it never turns a deny into anything, never
  replaces another rule's hold, and never allows. `deny_if_signal`, or any
  extra key inside `hold_if_signal`, is refused at load and at
  `PUT /v1/policies/{id}`. All three keys are required, and the threshold is
  `>=`. Name and value matching folds case and surrounding space.
- **Signals are an input, never fetched.** Wardryx believes a caller's signal
  the way it believes `chain_proven`, records the `source` the caller claims,
  and never branches on it. Nothing in `internal/pdp`, `internal/policy` or
  `internal/replay` makes a network call, and `decision-path-purity.sh` fails
  if anything those packages stand on in this module imports `net/http` or
  `os/exec`.
- **Recorded and replayable.** The decision event and the approval context
  carry every signal the decision read, and `wardryx replay` feeds the
  recorded signals back, so a signal hold reproduces with whatever produced
  the signal unreachable. The tool call is recorded as its name, target,
  sha-256 of the arguments and `arguments_truncated`, never the arguments.

## Changed

- **An approval is bound to the tool call a person read (wardryx#82,
  invariant 28).** When a hold is created for a request that carries a
  `tool_call`, the approval records `tool_call {name, target,
  arguments_truncated, digest}` (never the arguments), and the granted token
  carries the same digest in a signed, versioned claim (`v: 2`, `tcd`). A
  token bound to a call is refused for any other call (another argument,
  target, tool name or truncation, and the same JSON re-spaced) and on a
  request that carries no `tool_call`. Under a cost threshold the refusal is
  the same deny as any invalid token; under a signal hold the other call holds
  again with an approval of its own. A refused attempt does not spend a
  single-use token. `GET /v1/approvals` and `wardryx approvals` now show the
  tool and target being approved.
- The decision event's `tool_call` gains `digest`, so event, hold and token
  agree.
- **A decision under a policy carrying `hold_if_signal` is never
  `cacheable`**, whatever it decided, because a signal belongs to one call's
  arguments and a cache keyed on agent and tool set cannot see them.

## Documentation and tests

- The README states single-use as the approval-token default everywhere
  (wardryx#78), and two new tests hold the env table's Default column and the
  README prose outside it to the code's defaults (wardryx#79, wardryx#80).
- 394 test functions, up from 319 on 1.1.3, and `features/` gains
  `typed-risk-signal.feature` and `approval-bound-to-the-call.feature`, every
  scenario bound to a named test.

## Upgrade notes

- No new environment variable and no new route. `compat/1.0.json` is
  unchanged, since every change is additive.
- A policy that does not use `hold_if_signal` keeps its `PolicyVersion`
  (`TestAPolicyWithoutASignalRuleKeepsItsPolicyVersion`).
- Tokens: a hold created for a request with no `tool_call`, and every token
  minted before this release, are minted and verified exactly as before (no
  `v`, no `tcd`), so a mixed-version fleet during a rolling deploy still
  verifies them. A token with no digest also verifies on a request that
  carries a `tool_call`, so an enforcement point can start sending
  `tool_call` on the retry only without breaking tokens in flight.
- **Rollback:** a build from before 1.2.0 ignores `tcd`, so rolling back drops
  the call binding for tokens still inside their TTL (never wider than 1.1.3
  was).
- The digest is over the argument bytes as received, so the same JSON
  re-spaced is another call and is refused. An enforcement point must present
  the arguments it held, byte for byte.
- A caller that wants a hold on a signal must send `signals`; wardryx ships
  no signal producer. A proxy placed in front of `/v1/decide` can add them,
  and wardryx needs no change or setting for it.
- A 1.1.3 deployment moves to 1.2.0 by moving the image tag.

## Not proven

- No producer of signals exists in this repository, so the signal path is
  proven with caller-supplied signals only. No proxy that adds them was run
  against this wardryx here.
- TokenFuse's `tool_call` field names were taken from its source, not from a
  run against this build, and nothing was run against TokenFuse or Genaryx.
  The console's rendering of the new `context.tool_call` entry is not checked.
- The Postgres integration suite was not run locally, and the approval context
  round trip through JSONB was exercised only through the in-memory store
  (CI's `integration` job is the check).
- That the enforcement point executes the call it described: the caller is
  believed, the same boundary as a signal.
- A call whose arguments were truncated binds only its name, target and the
  flag.
- Behaviour of an older wardryx build against a `v: 2` token was reasoned
  (unknown claims are ignored), not run.
- `PUT /v1/policies` decodes leniently (pre-existing), so a misspelled key
  other than the ones refused here is still dropped there; file load is
  strict.
