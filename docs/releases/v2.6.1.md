# Wardryx 2.6.1

2.6.1 takes two event types off the shared bus and keeps what each one said. 2.6.0 added `approval_queue_full` and `policy_loaded` under `source: wardryx`, and agent-passport SPEC.md section 6.2, the registry a consumer reads to learn what a producer writes, lists neither. The decision of 2026-11-07 is that wardryx follows the registry and the registry does not follow wardryx (agent-passport#85 was closed), so a consumer never meets a wardryx type nobody told it about.

Nothing else moves: no decision, reason sentence, `policy_version`, approval, token, setting, schema or stored row changes, and no name `compat/1.0.json` freezes is removed or renamed.

## What became of each fact

- **An agent that reached its pending cap.** Every hold that found the queue full is recorded as `approval_requested` with `queue_full: true`, as it was in 2.6.0, so the fact stays on the bus in a type the registry lists. The separate event is now one structured line in the log, a warning, once per agent per process:

  ```
  2026/11/07 18:00:00 WARN wardryx: an agent reached its pending cap agent_id=agent://acme.example/agents/worker run_id=r1 pending_limit=20
  ```

  The agent id and the run id are the caller's words, so the line quotes them when they hold a space, a quote or a line break, and a line break in an id never starts a line of its own.

- **The policy set a process starts under.** One structured line in the log at start, after the store's policies are restored and before the first request, with the fields the event carried and the file the policy archive keeps that set in:

  ```
  2026/11/07 18:00:00 INFO wardryx: policy set loaded policy_version=6c5914b6007f policies=2 base_policies=2 no_grant_floors=[tool-hold] archived=/var/lib/wardryx/archive/6c5914b6007f.json
  ```

  With no `WARDRYX_POLICY_ARCHIVE` the last field reads `archived=none`. The archive already kept the set in force before the first decision, under the version's own name, and still does: the line says which set, and the archive holds it whole.

Both lines go where every other wardryx line goes, the process's standard error.

## Upgrade

Replace the 2.6.0 image with 2.6.1. No setting, stored state or schema step.

- **A consumer that read `approval_queue_full`**: read `queue_full` on `approval_requested`, which names the agent and the run on every such hold, or the warning line above from the service's log.
- **A consumer that read `policy_loaded`**: read the start line from the service's log, or fetch the set from the archive by the `policy_version` any decision names (`wardryx replay` does exactly that).
- **`wardryx replay`** counted neither type as a decision, so its report over a record does not change. A record 2.6.0 wrote keeps its two kinds of line; replay still reads past them.

## Rollback

Run the 2.6.0 image again. It writes the two types again; nothing stored changes, and no file or row 2.6.1 wrote is read differently by it.

## Changed

- **`approval_queue_full` is no longer written.** The pending cap is logged once per agent per process at warn level (invariant 48).
- **`policy_loaded` is no longer written.** The start is logged once at info level, with `policy_version`, `policies`, `base_policies`, `no_grant_floors` and `archived` (invariant 49).
- **A new gate, `scripts/bus-types-are-registered.sh`** (invariant 50). It reads the copy of the registry row in `internal/api/testdata/spec-6.2-wardryx.json` and every `s.emit`, `s.recordDecision` and `s.writeRecord` call, and fails on a type the row does not list, on a listed type at a severity the row does not give it, on a type or a severity it cannot read, on a listed type nothing writes, and on an `event.Event` literal outside `writeRecord`. It has nine cases in `scripts/gates-have-teeth.sh`. estate-gates C4 compares the registry itself with the code after a merge; this gate holds the copy before a push.
- **The tests read back what reached the bus against the row**, at its severity: the server's paths in `internal/api`, and the built binary's own record in `internal/manifest`.

## Limits

- A log line is not on the hash chain, and it lasts as long as the deployment keeps its logs. The chained record of each held call is its `approval_requested`, and the durable record of a policy set is the archive.
- With no archive, the start line is the only trace of the set a process started under.
