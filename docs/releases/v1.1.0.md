# Wardryx 1.1.0

One new route for an enforcement point that wants to know which offered tools
a policy would refuse. Nothing on the decision path moves.

## Added (wardryx#68)

- **`POST /v1/filter-tools`** answers "which of these offered tools would
  `deny_tool` refuse" rather than "may this action happen". It applies
  `Decide`'s tool rule to each offered tool alone, with the same matcher
  `Decide` uses, and answers `allowed` and `denied`, each denial naming its
  policy and rule, never null. No other rule applies: no chain, attestation,
  steps, domains, cost or approval rule.
- The route sits behind the same bearer authentication and body cap as
  `/v1/decide`; a missing `agent_id` is a 400 with a fixed message. Nothing
  is recorded, since no enforcement point acts on the answer.
- Invariant 21 holds the rule; `features/filter-tools.feature` binds its
  scenarios to tests. A seeded sweep over 200 policy sets requires `Filter`
  and `Decide` to agree on every tool alone, and seven planted faults were
  each caught by a named test.

## Who calls it

TokenFuse 1.1.0 calls it in shadow only (`TOKENFUSE_TOOLS_PRUNE=shadow`), to
measure the input tokens spent on the schemas of tools a policy would deny.
It never removes a tool from a forwarded request.

## Compatibility

Additive: `/v1/filter-tools` is listed as experimental in `compat/1.0.json`,
not frozen. `/v1/decide`, the policy fields and the event types do not move.
A 1.0.x deployment moves to 1.1.0 by moving the image tag.

## Limits

A filter answer writes no event, so it leaves nothing in the audit trail. It
applies `deny_tool` only: a tool it reports as allowed can still be refused
by `/v1/decide` under another rule. The Postgres integration suite for this
change ran in CI, not locally.
