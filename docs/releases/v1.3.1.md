# Wardryx 1.3.1

A policy file may hold several documents (YAML, separated by `---`) or several
values (JSON). Before this release only the first was read, and every later one
was dropped with no error. A PUT body with data after its policy stored the
policy and dropped the rest. This release loads every document and value, and
refuses data it cannot read as a policy.

## Fixed

- **Every document of a YAML policy file, and every value of a JSON policy file,
  is loaded (invariant 30).** Each holds one policy or a list of policies, as
  before, and they load in order. A YAML document with nothing in it holds no
  policy and is skipped. A JSON file with no value is refused, as before. A
  document or value that fails to decode fails the whole file, and the error
  names it by position, for example `document 2` or `value 2`. The strict field
  check applies to every one. Data after a JSON value that is not a whole value
  is refused, not ignored. A file with one document or value keeps its
  `PolicyVersion` byte for byte. A file with several has a version that covers
  every policy it loaded.
- The directory loader and `replay -policy` read files through the same decode,
  so they load every document and value too.
- **A PUT `/v1/policies/{id}` body with data after the policy is refused with a
  400.** Before, the policy was stored with a 200 and the rest was dropped without
  a word. The 400 does not echo the refused data, and nothing is stored.
  Whitespace after the policy is still accepted. The other JSON request bodies
  (decide, filter-tools, approval decide) are read as before.

## Upgrade

A policy file with more than one YAML document, or more than one JSON value, now
enforces all of them. A call that was allowed only because a later document's or
value's deny was dropped can now be denied. A later `require_human_above_usd` or
`deny_above_usd` now applies as well. Read your policy files before you upgrade.

A file that no longer loads, because a later document or value has a misspelled
field, a value of the wrong type, or data that is not a whole value, stops
`serve` and `check` at start, and the error names the document or value.

A JSON policy file with data after its first value, such as a second object or a
stray fragment, now fails to load. Before, that data was ignored.

A PUT that carried data after the policy now gets a 400 and is not stored. A
client that sent such a body was writing a policy the server never kept, so check
any tooling that does this. Ordinary bodies, including ones with a trailing
newline, are unaffected.

Rolling back to 1.3.0 brings back the silent drops for the same files and bodies.

## Not proven

- No live deployment's policy files or PUT traffic were read, so how many calls
  change their verdict on upgrade is not known.
- The policy, pdp and api packages were tested locally, together with the gates
  in `CLAUDE.md`. The Postgres integration suite, `govulncheck` and `gosec` run
  in CI and were not run here. No image was built.
- A PUT body with a misspelled field (for example `deny_tolls`) is still stored
  with a 200, and the field is dropped. Refusing unknown fields there would also
  refuse a body copied from a GET, so that is a separate decision and this release
  does not change it.
- Load cost was not measured. Each document or value is decoded again from the
  start of the file, so the work grows with the square of their count. That is
  fine for a handful and was not measured for a large file.
