# Wardryx 2.3.0

2.3.0 lets wardryx check an agent's own token, and the proof that the agent holds the key the token is bound to, instead of taking the enforcement point's word for who the agent is. The check is opt-in: with `WARDRYX_AGENT_TOKEN_ISSUER` unset, every decision is made as 2.2.1 made it. The release also keeps each configured bearer key under its SHA-256 digest, which an operator does not see. The new settings and refusals are additive and sit behind the issuer setting, so this is a minor release. No name `compat/1.0.json` freezes is removed or renamed.

## Upgrade

Nothing changes unless `WARDRYX_AGENT_TOKEN_ISSUER` is set. Without it, a token sent in `agent_token` is ignored (logged once per process), and the request's own identity source stands, as before. The bearer key store change is invisible to operators: keys are configured as before, and `key_fp` in every audit record is the same 16 hex characters.

With `WARDRYX_AGENT_TOKEN_ISSUER` set:

- `WARDRYX_AGENT_TOKEN_AUDIENCES`, one of `WARDRYX_AGENT_TOKEN_JWKS_URL` or `WARDRYX_AGENT_TOKEN_JWKS_FILE`, and `WARDRYX_AGENT_TOKEN_DOOR_ORIGINS` are required with it. A partial set refuses to start. So does any of these settings made without the issuer.
- A proof is required by default. The agent sends `agent_dpop_proof` with its token, and a token with no proof is refused with `403 agent_token_proof_required`. `WARDRYX_AGENT_TOKEN_REQUIRE_PROOF=0` turns the requirement off and prints a warning at startup. Then a token alone is usable by whoever holds it, through any configured door.
- Every enforcement point that sends `agent_token` must also send `agent_dpop_proof`. Unless `WARDRYX_AGENT_TOKEN_REQUIRE_PROOF=0` is set, each of its agent-token calls is refused until it does. tokenfuse is the enforcement point that sends both fields. It does so from the release that includes TAIPANBOX/tokenfuse#471, which was still open when these notes were written, so check the tokenfuse release you run before you set the issuer.
- The refusals on `/v1/decide` are all `403`: `agent_token_required` (the request claims the `agent-token` source and sends no token), `agent_token_invalid` (the token does not verify), `agent_contradicts_token` (the token verifies for another agent), `agent_token_proof_required` and `agent_token_proof_invalid` (the proof is missing or does not verify). A verified token that names another agent also writes an `identity_mismatch` event.

## Breaking

None. A deployment that does not set `WARDRYX_AGENT_TOKEN_ISSUER` is unaffected. A deployment that sets it gets the refusals listed under Upgrade, which are new and sit behind that setting.

## Migration: switching on the agent token check

1. Check the enforcement point first. It must send `agent_dpop_proof` with each `agent_token`. The proof is made with the key the token is bound to, names that token, and is sent to one of the doors listed in step 5. tokenfuse sends both fields from the release that includes TAIPANBOX/tokenfuse#471, which was still open when these notes were written.
2. Set `WARDRYX_AGENT_TOKEN_ISSUER` to the exact `iss` of the agent tokens.
3. Set `WARDRYX_AGENT_TOKEN_AUDIENCES` to a comma-separated list of the audiences this wardryx accepts a token for.
4. Set `WARDRYX_AGENT_TOKEN_JWKS_URL` (an `http` or `https` URL, polled every 30 seconds), or `WARDRYX_AGENT_TOKEN_JWKS_FILE` (re-read on each refresh), or both. The key set is read at startup, and a process whose key set cannot be read does not start.
5. Set `WARDRYX_AGENT_TOKEN_DOOR_ORIGINS` to the origins of the doors, comma-separated. Each is `scheme://host:port` with nothing after the port. A path or userinfo refuses to start, and the default port is filled in.
6. Optional: `WARDRYX_AGENT_TOKEN_REVOCATION_URL`, an `http` or `https` URL polled every 30 seconds. With none, no token is revoked by a list. With one that has never been fetched, every token is refused.
7. Optional: `WARDRYX_AGENT_TOKEN_PROOF_MAX_AGE_SECONDS`, a whole number from 1 to 300. The default is 60, and any other value refuses to start.
8. Leave `WARDRYX_AGENT_TOKEN_REQUIRE_PROOF` unset. It is `1` by default, `0` turns the proof off, and any other value refuses to start.
9. Start wardryx and read the startup output. Then watch for the `403` reasons above on `/v1/decide`.

**Rollback.** A 2.2.1 build ignores these settings, so rolling back removes the check, and the request's own identity source is believed again, as before this release. No stored state changes. The bearer key store is held in memory and rebuilt from `WARDRYX_KEYS` at start, and the events file keeps the lines written before the rollback.

## Added

- Eight optional variables, `WARDRYX_AGENT_TOKEN_ISSUER`, `WARDRYX_AGENT_TOKEN_JWKS_URL`, `WARDRYX_AGENT_TOKEN_JWKS_FILE`, `WARDRYX_AGENT_TOKEN_AUDIENCES`, `WARDRYX_AGENT_TOKEN_REVOCATION_URL`, `WARDRYX_AGENT_TOKEN_DOOR_ORIGINS`, `WARDRYX_AGENT_TOKEN_REQUIRE_PROOF` and `WARDRYX_AGENT_TOKEN_PROOF_MAX_AGE_SECONDS`, all unset by default. The README's environment table gives each one's default.
- Two optional request fields on `/v1/decide`: `agent_token`, the agent's own token, and `agent_dpop_proof`, the proof sent with it.
- The verification itself. The token's signature is checked under the key its `kid` names in the set wardryx holds. Its issuer, audience, expiry (with 30 seconds of leeway), not-before and subject are checked, and the subject must equal the request's `agent_id`. The revocation list is checked last. The proof's key must match the token's `cnf.jkt`, the proof's signature, `ath`, freshness, `htm` and `jti` are checked, and its `htu` origin must be one of the configured doors. The token and key work uses the relayed-token check of agent-stack-go v2.
- The `identity_mismatch` event, under source `wardryx`, written when a verified token names a different agent than the request. Its data names the route, the asserted agent and run, the token's subject, and the key's org, role and fingerprint, never the key. The event is registered in agent-passport SPEC 6.2 (agent-passport#81).

## Changed

- `/v1/decide` decides the identity source. With the issuer set, a token that verifies sets the source to `agent-token`, and that value is wardryx's own check. A request that claims `agent-token` with no token is refused. With the issuer unset, the request's claim stands as before.
- Bearer keys are stored under the SHA-256 digest of each key, and a presented bearer is looked up by its digest. `key_fp` is unchanged.
- `CLAUDE.md` invariant 13 is rewritten. It states what wardryx verifies itself and what it still trusts, and the Upgrade section above repeats the part an operator needs. A new invariant 42 holds the bearer lookup rule, with its gate `scripts/no-raw-secret-lookup.sh`.
- `components.json` declares the eight settings as optional.
- The README gains eight rows in the environment table and a line in its checklist.
- `COMPATIBILITY.md` is regenerated from `compat/1.0.json`. The new settings, the two request fields and the new refusals are listed under additive.

## Security fixes, by what they close

- A presented bearer was matched against the configured keys by its raw value. The key store now holds the SHA-256 digest of each configured key, and a presented bearer is looked up by its digest, so no configured key sits in the store in the clear. The timing of that lookup was not measured (see below).
- An agent's identity came from the enforcement point's word alone. With the issuer set, wardryx verifies the agent's token itself, and refuses a token that names another agent. The enforcement point can still skip wardryx (see below).
- A token held by someone other than the agent was enough on its own. With the proof required, a request must also carry a proof made by the key the token is bound to, for that token, sent to a configured door and fresh. A proof captured within its window can still be replayed (see below).

## Documentation and tests

- 614 test functions, the README badge's count, up from 575 in 2.2.1: 3 for the key store and 36 for the token check.
- `features/bearer-key-store.feature` has 4 scenarios, and `features/agent-token-verified-by-wardryx.feature` has 30. `scripts/scenarios-bind-to-tests.sh` reports 248 scenarios and 322 bindings, each naming a test that exists.
- Invariant 42 has `scripts/no-raw-secret-lookup.sh`, with four cases in `scripts/gates-have-teeth.sh`.
- Mutants planted on the proof's key comparison, its `ath` check, its window and its door check were each caught by a named test.

## Not proven: where it says nothing

- No run against a live vouchryx or a real enforcement point. The tests mint tokens and proofs with generated keys.
- A proof is not remembered. A proof captured within its window (60 seconds by default, 300 at most) can be presented again at any configured door, for as long as its token lives (five minutes). Nothing in wardryx refuses the second use. The door that first saw the proof could refuse it, and that door does not reach wardryx.
- The enforcement point can skip wardryx and decide without it. A request that carries no token keeps the source it claims. `chain_proven` and `attestation_method` remain the enforcement point's word.
- `htm` is checked for presence, not against the method of the call. A proof's `jti` is checked for presence and length, and is not remembered.
- The timing of the digest lookup was not measured. The lookup compares digests, not the secret itself.
- The Postgres integration suite was not run here, because it needs `DATABASE_URL`. `internal/store` is unchanged.
