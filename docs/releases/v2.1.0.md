# Wardryx 2.1.0

2.1.0 lets a policy require the identity source the enforcement point reports,
and it changes one answer on the failure path: an allow or a hold is no longer
returned when its record cannot be written, unless the operator chooses
`WARDRYX_RECORD_FAILMODE=open`. Read **Breaking**, **Behaviour change on the
failure path** and **Migration** before upgrading. Everything else is additive,
and no name `compat/1.0.json` freezes is removed or renamed.

## Breaking

- **An allow or a hold whose record cannot be written is refused by default.**
  This applies only when `WARDRYX_EVENTS_PATH` is set. Under the default `closed`
  fail mode, `POST /v1/decide` answers `503` with `record_unavailable` where 2.0.0
  answered `200`. A deny is unchanged. The next section says what else changes.

## Behaviour change on the failure path

When an event file is configured and a record write fails:

- **Allow and hold.** wardryx writes the record before it returns an allow or a
  hold. Under `WARDRYX_RECORD_FAILMODE=closed`, the default, a failed write means
  the caller gets `503` with `{"error": "record_unavailable"}` and no decision, so
  nothing acts on an answer that no record holds. Under `open`, the answer is
  returned as in 2.0.0. Any value other than `open` is closed. `serve` logs a
  warning at startup when `open` is chosen.
- **Readiness.** While any record write is failing, `GET /readyz` answers `503`
  with `"record": "failing"`, in either fail mode. The body is unchanged while the
  store answers and no record write fails. The log carries one line when a record
  starts failing and one when a write succeeds again. A readiness probe that reads
  `/readyz` takes the instance out of rotation during a record failure.
- **Deny, approval and policy records.** A deny is returned whether or not its
  record was written: it starts no action, and refusing it would trade a known
  refusal for an unknown one. The records of approval grants and denials and of
  policy writes stay fail-open. A failure of any of them still marks `/readyz`.
- **No event file.** With `WARDRYX_EVENTS_PATH` unset there is no record, nothing
  can fail to be written, and nothing is refused.

## Migration

1. **A healthy event file needs no change.** Where the record is written, allows
   and holds are returned as before.
2. **A launcher that must keep answering on a failing record disk** sets
   `WARDRYX_RECORD_FAILMODE=open`, and watches `/readyz`, which answers `503` while
   the record fails.
3. **A readiness probe on `/readyz`** should expect a record failure to remove the
   instance from rotation in either fail mode.
4. **A single-use approval token redeemed for an allow that closed then refuses**
   stays spent, so a person grants again. A refused hold stays pending in the
   approval queue.
5. **Identity source is optional.** Nothing changes until a policy sets
   `require_identity_source`. Before you add that field, have the enforcement point
   send `identity_source` on `/v1/decide`. Under a policy that lists sources, a
   request that sends none, or an unlisted value, is denied, and every matched
   policy's list must name the request's source.
6. **Replay.** A record written before this release has no source and replays as
   `none`. Nothing is unreadable. A replay under a policy that now requires a
   source reports the change.
7. **`wardryx check`** has no enforcement point, so it judges a
   `require_identity_source` rule as `none`.

## Added

- `identity_source`, an optional field on `POST /v1/decide`: how the enforcement
  point knew the agent. One of `agent-token` (it verified an agent token at its own
  door), `client-key` (a static key) or `none`. An absent value, or any other value,
  is `none`. Every decision event records the normalized source.
- `require_identity_source`, a policy field: the sources the policy accepts. A
  value other than the three is refused at load, and the error names it. The rule
  denies a request whose source is not listed and never holds it.
- `WARDRYX_RECORD_FAILMODE`, an optional variable: `closed` (the default) or
  `open`.
- The `503 record_unavailable` answer, the `"record": "failing"` field on
  `/readyz`, and the startup warning for `open`.

## Changed

- `/readyz` answers `503` while any record write is failing, in either fail mode.
  Its body is unchanged while healthy.
- A decision under a policy that sets `require_identity_source` is never cacheable,
  because the source belongs to the request and not to the agent and tool set a
  cache is keyed on.
- `components.json` declares `WARDRYX_RECORD_FAILMODE` as an optional variable.

## Security fixes, by what they close

- A policy could not say that it accepts only agents the enforcement point
  verified. `require_identity_source` names the sources a policy accepts, so a rule
  for verified agents is not satisfied by a request that carried no source.
- An allow or a hold could be returned to a caller although its record had not
  been written, so a decision could be acted on with no record of it. Under the
  default it is now refused.

## Upgrade notes

- No new route. The additions are listed under additive in `COMPATIBILITY.md`, and
  `scripts/compat-surface.sh` holds the frozen surface.
- **Rollback.** A 2.0.0 build refuses to load a policy file that names
  `require_identity_source`, because its file decoder is strict, and refuses a
  `PUT` of such a policy with a `400`. A 2.0.0 build reads a stored policy with a
  decoder that drops fields it does not know, so a stored policy that requires a
  source would silently lose that rule. Remove `require_identity_source` from every
  policy, stored or file, before rolling back. A 2.0.0 build ignores
  `identity_source` on `/v1/decide` and does not read `WARDRYX_RECORD_FAILMODE`, so
  it returns allows and holds whose record failed, as 2.0.0 did.

## Documentation and tests

- 539 test functions, up from 511 in 2.0.0. Two feature files bind their scenarios
  to named tests: `features/a-policy-can-require-a-verified-agent.feature` and
  `features/record-failmode.feature`.
- CLAUDE.md invariants 39 and 40. Invariant 39 is held by the order gate
  `scripts/decide-order-is-documented.sh`, which reads the rule's place in
  `Decide`. Invariant 40 is held by `scripts/decision-record-is-checked.sh`, a new
  gate. `scripts/gates-have-teeth.sh` plants a fault for each.
- The README sections "Decision engine" and "The record of a decision" describe
  the rules above.

## Not proven: where it says nothing

- No live enforcement point sends `identity_source` yet. TokenFuse's side is not
  part of this release, so the field has no live sender to test against.
- wardryx trusts the source the enforcement point reports. A point that reports a
  stronger source than it had is not caught. The rule bounds what a policy accepts;
  it does not verify a token.
- The closed default was tested with a refusing sink double. A real write failure
  through agent-stack-go's chained writer, such as a full volume or a read-only
  file, was not run, and no launcher was brought up against this build.
- A single-use token redeemed for an allow that closed then refused stays spent, and
  no test pins a re-grant flow for it.
- Postgres paths are unchanged in this release. The Postgres integration job runs
  in CI, not here.
