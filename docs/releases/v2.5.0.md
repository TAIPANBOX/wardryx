# Wardryx 2.5.0

2.5.0 makes two changes to what wardryx does with an agent's calls. With a database configured, the record of accepted DPoP proofs is shared by every instance and survives a restart, so a proof spent at one instance is refused at the next. And an agent that has spent its error budget can now have its tool calls put to a person automatically, from the event file the quality plane (verdryx) writes.

It is a minor release. The second change is off unless its setting is set. The first changes behaviour only for a deployment that sets both `WARDRYX_DB` and `WARDRYX_AGENT_TOKEN_ISSUER`, and the Upgrade section says what to check for it. A deployment that sets neither decides as 2.4.1 did.

## Upgrade

- **`WARDRYX_DB` and `WARDRYX_AGENT_TOKEN_ISSUER` both set.** The schema gains the table `agent_proof_replays`, applied at start the way the rest of the schema is, so there is no manual step. Each proof that passes every other check is claimed in that table by one atomic insert. A decide that carries a proof now needs the database to answer: when the store is gone the call is refused with `503 agent_token_proof_unrecorded`, and when the store answers with a failure of its own the call is refused with `500`. A decide with no proof does not touch the table. The process does not stand in for a record it cannot reach, because a proof nobody could check for replay may be a replay.
- **`WARDRYX_AGENT_TOKEN_ISSUER` set, `WARDRYX_DB` unset.** The record stays in the process, as in 2.4.1. `serve` now says so at start, and the README states the limit in its environment table and its Security section.
- **`WARDRYX_SIGNAL_EVENTS` unset.** Nothing changes. No file is read, no signal is added, and a decision carries the same `policy_version`.
- **Database connections.** The pool is bounded at 16 connections, open and idle alike. At the library defaults, 32 concurrent callers opened 2241 sessions for 5952 decides; with the bound the same kind of run used 42 sessions for 8928 decides.

**Rollback.** Run the 2.4.1 image again. It does not read `agent_proof_replays`, and the table can stay in the database. The proof record goes back to the process, so a restart clears it again.

## Added

- **Shared proof record.** With `WARDRYX_DB` set, the table `agent_proof_replays` is the record of accepted proofs. The key is a SHA-256 over a tag, the holder's key thumbprint and the proof's `jti`, so no client byte reaches SQL and one holder cannot spend another holder's `jti`. A row lasts until the proof's `iat` plus 300 seconds, the longest window there is, whatever window the writing instance uses. A purge runs at start and every minute and removes rows 300 seconds past that, by the database's clock.
- **`503 agent_token_proof_unrecorded`** on `/v1/decide`, for a proof that could not be recorded because the store is unavailable. It is not a 403, because the proof may be good and the caller's next fresh proof may be answered.
- **`WARDRYX_SIGNAL_EVENTS`** and **`WARDRYX_SIGNAL_EVENTS_MAX_AGE`**, both optional. `WARDRYX_SIGNAL_EVENTS` is the path of the verdryx event file, read-only. The age is how long an event signals after its time, 48 hours by default, from one minute to thirty days; an age with no file, or outside that range, refuses to start.
- **The `slo_burn` signal.** With the file set, every decision carries one standing signal named `slo_burn` for the agent it is about, with value `exhausted`, `fast_burn`, `unmeasured` or `none`, at probability 1. A policy rule reads it with `hold_if_signal`, and a granted approval lets that one call through, as for any hold. The example policy is `docs/examples/hold-while-the-budget-is-spent.yaml`.
- **`/readyz` member `signal_events`** (`ok`, `unreadable` or `broken`), present only while the setting is set. It never changes the status code.

## Changed

- **An unmeasured burn is not health.** A `fast_burn` event whose `burn_events_seen` is missing, zero, negative, fractional or not a number reads as `unmeasured`, never `none` and never `fast_burn`. An `exhausted` event stands on the budget, so its count does not matter. `none` says only that the file is sound and holds no live event for the agent.
- **The signal can only add a hold.** `internal/pdp` and `internal/policy` are not touched. A caller's own `slo_burn` signal is dropped, so it cannot remove the real one, and while the setting is set a request may carry 15 signals of its own instead of 16. A recorded decision replays with the file gone.
- **A file that cannot be believed is loud.** A broken hash chain, a malformed line, a restart, a chain that starts mid-way, a bad time or one more than five minutes ahead, or a file over 32 MiB reads as `broken`. A missing file, or one that is not a plain file, reads as `unreadable`. The log names the file and the reason once per change. Under `when_absent: hold`, an unreadable file holds the tool calls of the agents the rule matches.
- **Database outages are recognised more widely.** A connection that ends during a call and a server that reports it is stopping, starting, full or read-only now count as the store being unavailable. They read as a plain 500 before.
- **The claim has its own deadline** and does not end when the caller hangs up, so a cancelled claim does not cost a session or hide a hanging store.
- **Cost.** A proof with the shared record costs a database write, about 420 bytes of WAL. On a 4-core Intel N150 with client, wardryx and Postgres on one box, one caller measured p50 2.3 ms and p99 5.1 ms against p50 0.42 ms and p99 0.91 ms with the record in the process. The `slo_burn` signal adds about 8 microseconds and 12 allocations per decision through the handler, and 171 bytes per decision record.
- **Dependency.** `agent-stack-go` moves to v2.0.2, the Go 1.27.3 rebuild, with no API change. The CI actions group is updated.

## Limits

- The event file's hash chain shows that a line was not edited or removed from the middle. It does not say who wrote the file and cannot see lines cut from its end, so the file is as trustworthy as its permissions.
- An event is matched to an agent by exact `agent_id`, in no org.
- The quality plane writes no event on recovery. An agent leaves the hold when a weaker event replaces the exhausted one or the age runs out.
- Verdryx writes `fast_burn` only when an indicator's interval is wholly below its target, so today's file carries `exhausted` events and `fast_burn` is read when it arrives.
- A crash while the file is being written leaves it `broken` until it is moved aside.
