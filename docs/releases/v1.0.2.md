# Wardryx 1.0.2

One fix, no wire change, the sibling of 1.0.1's: `wardryx replay` no longer
reports a deny on an approval token that did not verify as the record and the
code disagreeing about the past.

## The defect (wardryx#59)

Seen while fixing #57. A caller that presents an approval_token which fails
verification (expired, forged, bound to another agent, run or tool set) is
denied, with the verifier's reason after `presented approval_token is
invalid`. The token is never recorded (invariant 15), so replay presents
nothing and reaches the plain hold: recorded deny, replayed hold, and 1.0.1
filed the row under `diverged`, with the banner that nothing below it is
trustworthy.

## The fix

- A seventh row, `approval-refused`, beside `approval-decided` and
  `approval-spent`: the PDP denied what was presented; replay reaches the
  hold; the row is replayable and the counterfactual is measured against the
  hold.
- The phrase is a shared constant now, `pdp.ReasonApprovalRefused`, written
  by `Decide` in one position (after the threshold sentence, before the
  verifier's error) and matched by replay in that position and no other; a
  deny past the threshold with any other reason is still a divergence.
- A token is only ever inspected past the threshold, so `approval-decided`,
  `approval-spent` and `approval-refused` are every way a credential the
  record does not carry can move a verdict. Invariant 18 says so; three
  scenarios bound to three tests, each red first against 1.0.1's replay, the
  third driving the real handler, its real file and the real replay.

## Compatibility

Additive: a new row in the replay report (experimental in `compat/1.0.json`);
nothing on the wire, in the routes, in the policy fields or in the event
types moves. A 1.0.x deployment moves to 1.0.2 by moving the image tag;
nothing to migrate. Records written by 1.0.0 and 1.0.1 are read the same way,
since the phrase they carry is the one this release matches.
