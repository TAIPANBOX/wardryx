# Wardryx 2.2.0

2.2.0 lets an operator have Keyryx, the key custody service, sign approval tokens.
A grant made with `WARDRYX_APPROVAL_SIGNER=keyryx` is signed with a key that Keyryx
holds, and wardryx verifies the token from a set of public keys it caches, so a
party that can check an approval cannot make one. The change is opt-in: with no
signer set, this release decides and approves as 2.1.0 did. Read **Migration**
before you switch the signer on. Nothing else changes, and no name
`compat/1.0.json` freezes is removed or renamed.

## Breaking

None. A deployment that does not set `WARDRYX_APPROVAL_SIGNER` is unaffected. A
deployment that sets it must also set `WARDRYX_APPROVAL_V2_UNTIL`, or the HMAC
tokens of holds granted before the switch are refused. See **Migration**.

## Added

- `WARDRYX_APPROVAL_SIGNER`, an optional variable. Empty, the default, mints the
  HMAC token under `WARDRYX_APPROVAL_SECRET`, as before. `keyryx` signs the token
  through Keyryx. Any other value refuses to start, and the error names the value.
- `WARDRYX_KEYRYX_URL`, an optional variable, required with `keyryx`: Keyryx's
  custody endpoint, an `http://` or `https://` URL, or `unix:///path` for its socket.
- `WARDRYX_KEYRYX_CREDENTIAL_FILE`, an optional variable: a file holding the bearer
  key wardryx presents to Keyryx over `http`. A socket needs none, because Keyryx
  knows its caller by the socket it was reached on.
- `WARDRYX_APPROVAL_V2_UNTIL`, an optional variable: an RFC 3339 instant. An HMAC
  token verifies before it and is refused at or after it.
- The v3 approval token, described below.
- The answer `503` with the message "the approval signing service is unavailable;
  the hold stays pending" for a grant that Keyryx cannot sign.
- A startup line that names the signer, the key and the deadline, for example
  `approval tokens are signed by Keyryx (key wardryx-approval at ...); v2 tokens
  verify until 2026-11-01T00:00:00Z`.

## The v3 approval token, for operators

- The token is three base64url segments separated by dots: a header, the claims,
  and a signature. The signature is raw ES256, the 64-byte `r || s` form.
- The header is `alg` (always `ES256`), `kid` (the RFC 7638 thumbprint of the key
  that signed) and `typ` (always `wardryx-approval+jwt`). Any other member, including
  a key or a key location, is refused.
- The claims are `v` (3), `aid` (the approval id), `agent_id`, `run_id`, `tools`
  (sorted), `max_cost_usd`, `tcd` when the hold named a tool call (the same digest
  a v2 token carries), `exp` (ten minutes after the grant) and `nonce`.
- The checks are the ones a v2 token passes: agent, run, tool set, call digest,
  cost ceiling and expiry. A token bound to a tool call is refused for any other
  call. A token granted with no call is refused where a call must be bound.
- The key that verifies a token is one wardryx holds. It fetches Keyryx's published
  set for the key `wardryx-approval` once at start and then every minute. A `kid` the
  set does not hold is refused. A set with any member that does not verify is
  refused whole, and the keys already held keep verifying.
- The key name `wardryx-approval` and the purpose `approval` are fixed in this
  release.
- A caller still receives and sends the token as an opaque string in
  `approval_token`. A caller that splits the token on dots to read its claims sees
  three segments where a v2 token has two.

## Changed

- A grant is signed before its decision is written. With a signer set, a grant that
  Keyryx cannot sign answers `503` and the approval stays pending, so a later grant
  can succeed. A grant of an approval that is already decided answers `409` before
  anything is signed, as it did.
- With a signer set, `WARDRYX_APPROVAL_SECRET` is not needed to grant. It is still
  needed to verify HMAC tokens inside their window.
- The startup warning about an empty `WARDRYX_APPROVAL_SECRET` is not printed when a
  signer is set.
- `components.json` declares the four new variables as optional.
- The README's approval section describes both token forms and the four variables.

## Security fixes, by what they close

- Anyone who held `WARDRYX_APPROVAL_SECRET` could mint an approval, and anyone who
  verified one needed the same secret, so a verifier could mint too. With
  `WARDRYX_APPROVAL_SIGNER=keyryx` the signing key is held by Keyryx. A verifier
  needs only the published key set, so nothing a verifier holds can mint an
  approval, and anyone with the published set can check a token without wardryx.
- A token that names a key the verifier does not hold is refused, and a token cannot
  carry the key that verifies it.

## Upgrade notes

- No new route. The frozen surface in `compat/1.0.json` is unchanged. The additions
  are listed under additive in `COMPATIBILITY.md`, which `scripts/compat-surface.sh`
  renders from the manifest.
- **Rollback.** A 2.1.0 build reads only the HMAC form. It checks a v3 token's
  signature against the HMAC secret, so it refuses every v3 token. After a rollback,
  an approval granted with the signer holds again: the rollback fails closed and
  never allows one. A 2.1.0 build with `WARDRYX_APPROVAL_SECRET` empty refuses every
  grant with `500`. Before you roll back, set `WARDRYX_APPROVAL_SECRET`, and unset
  `WARDRYX_APPROVAL_SIGNER` so grants mint HMAC tokens again.

## Migration: switching on Keyryx signing

1. Give Keyryx the approval key `wardryx-approval`, and let the consumer that wardryx
   is reached as sign with it for the purpose `approval`. Keyryx names a consumer by
   the socket or key file it is reached through, so wardryx sends no name of its own.
2. Set `WARDRYX_APPROVAL_SIGNER=keyryx` and `WARDRYX_KEYRYX_URL`. Over `http`, also
   set `WARDRYX_KEYRYX_CREDENTIAL_FILE` to a file holding the bearer key, readable by
   the wardryx user only.
3. Set `WARDRYX_APPROVAL_V2_UNTIL` to an instant no earlier than ten minutes after
   the switch, the lifetime of a grant. Without it, every HMAC token is refused from
   the first request, so holds granted before the switch hold again.
4. Start wardryx and read the startup line. A v3 token is refused until the first key
   set has been fetched, which happens at start and then every minute. A grant does
   not need that set, so it works as soon as Keyryx answers.
5. Remove `WARDRYX_APPROVAL_SECRET` only after `WARDRYX_APPROVAL_V2_UNTIL` has passed.
   Until then it verifies the HMAC tokens still in flight.

While Keyryx is unreachable, a grant answers `503` and the hold stays pending. A
token already granted keeps verifying on the keys wardryx holds.

## Documentation and tests

- 575 test functions, the badge's count, up from 539 in 2.1.0. The approval change
  adds 36 of them.
- `features/approval-token-v3.feature` has 11 scenarios, each bound to named tests.
- CLAUDE.md invariant 4 is amended to cover both token forms, and invariant 41 is
  added. Its gate is `scripts/approval-verifier-trusts-its-keys.sh`, with five cases
  in `scripts/gates-have-teeth.sh`.
- `scripts/agent-is-bound-to-its-key.sh` also reads `approval.DecideWith`, the grant
  path that now signs.
- Eight mutants were planted on the verifier and the grant path, each caught by a
  named test: a signature not checked, a cache that answers with any key, a v2 token
  accepted after its deadline, an agent binding not compared, a call digest not
  compared, a header algorithm not pinned, a failed mint that no longer stops the
  grant, and an unsignable grant that still decides.

## Not proven: where it says nothing

- No run against a live Keyryx. The sign route, the inventory and the published set
  were read from Keyryx's source, and the tests use a stand-in for Keyryx. Run a grant
  against a real Keyryx before a rollout.
- The ES256 signature format, raw `r || s` over the SHA-256 of the signing input, was
  read from Keyryx's source. It is not exercised across the two programs.
- Two grants of one approval can race. Both are signed, one is refused with `409`,
  and the unused signature stays in Keyryx's use log.
- A cached key set has no age bound while Keyryx is unreachable. A revoked kid keeps
  verifying until the next successful fetch.
- A rollback to 2.1.0 is reasoned from its source, not run.
- The Postgres integration suite is not run here. This change does not touch the store.
