# Wardryx 2.6.0

2.6.0 lets a policy file say that a tool call of an agent nothing grants is held for a person. Model calls still pass, and only an explicit grant lifts the hold: a restriction never does.

It is a minor release, and it does nothing until a floor is in a policy file. **A policy file with neither `when_no_grant` nor `grant_tool` behaves as before, with the same `policy_version`**, and no new setting needs to be set. This repository ships no floor: a deployment or a launcher that writes one decides. The one step every deployment with a database goes through is the schema change below, which is applied at start.

## Upgrade

- **A policy file with neither field.** Replace the 2.5.1 image with 2.6.0. Every decision, reason and `policy_version` stays what it was, holds are written to the queue as they were, and `wardryx check` prints what it printed. Two things you can see: `serve` writes one `policy_loaded` event at start, and the unanswered-approval sweep reads pending rows only, which changes what it costs and not what it reports.
- **`WARDRYX_DB` set: the schema step.** The table `approvals` gains a nullable column, `pending_key`, and two partial indexes, `approvals_pending_call` (unique, on agent, run and key, over pending rows that have a key) and `approvals_pending` (on agent and time, over pending rows). They are applied at start the way the rest of the schema is, so there is no manual step. It is safe on a database that already holds identical pending rows: every existing row has no key, and a row with no key is outside the unique index, so nothing can conflict. The indexes are built in the start's own statement, so writes to `approvals` wait for that build the first time. With no database there is no step.
- **Several instances.** Move every instance to 2.6.0 before any file carries either field. A 2.5.1 instance refuses such a file at load.
- **Turning the floor on.** Do it after the upgrade, as a change of its own, in this order:
  1. Ask what it would hold: `wardryx replay -policy <candidate>` reads what your agents actually did and lists each agent and tool that would wait for a person, how often and when last. `-format json` prints the same run for a program. Read `unexamined` beside it: a report of nothing over a history that could not be replayed says nothing.
  2. Write the grants, on targets that name a trust domain, and ask again until the list is what you meant.
  3. Add the floor to the file and restart. The file is read at start and at no other time. `docs/examples/tool-hold.yaml` is the floor as it is meant to be written.

  Do not use an enforcement point's shadow mode for this: wardryx does not know the mode, so every hold writes a row, about a call that went through.
- **`WARDRYX_PENDING_PER_AGENT`** is new and optional. Unset is 20, and anything but a whole number of at least 1 refuses to start. It reads nothing with no floor.

## Rollback

**Take the floor out of the file and restart first, and only then change the image.** A wardryx older than this one refuses `when_no_grant` and `grant_tool` at load, so a rollback in the other order is a service that does not start, and an enforcement point that fails closed then refuses everything. The steps:

1. Remove `when_no_grant` and every `grant_tool` from the policy file, and restart 2.6.0 on it. Tool calls pass as they did before the floor.
2. Run the 2.5.1 image.

The column and the indexes can stay in the database: 2.5.1 neither reads nor writes `pending_key`, its rows have none, and they fall outside the unique index. A `grant_tool` written through `PUT` can stay too: 2.5.1 reads a stored policy with a decoder that drops the key, and the row keeps it for a later upgrade. Run `wardryx replay` from 2.6.0 over decisions recorded under a floor: 2.5.1 drops the field from the archived set too, and reports them as diverged.

## Added

- **`when_no_grant: hold`, the floor.** Rule 15 of `Decide`, after rule 14 and before the final allow, holds a request that carries a `tool_call` when any tool it names, in `tool_names` or as the call's name, is not granted. A request with no `tool_call` is not judged. The rule runs after every other rule, so it turns an allow into a hold and changes no other verdict. `allow` is the default and is stored as absent; `deny` is refused at load, and so is a value that is blank, null or not text, each in a sentence that says what to write.
- **`grant_tool`.** A tool is granted by a matched policy, in the org of the decision, whose target pins a trust domain (`agent://acme.example`, `agent://acme.example/...`) and which names it in `grant_tool` or `allow_tool`; `grant_tool: ["*"]` is every tool. Nothing else counts: a `deny_tool`, a `max_steps` or a `hold_if_signal` lifts nothing, so hardening a fleet cannot switch the control off. A grant lifts the floor and no other rule. It is refused at load on a target with no domain in it, in the policy that holds the floor, and with a blank entry or a `*` beside other text.
- **A person answers a hold of the floor like any other.** The approval carries the tool and target, and `hold_kind: no_grant` in its context. Only a token bound to the call lifts the hold, once under the single-use default; any other token holds again with the same reason and never denies. On a call rule 15 would hold, a token that binds no call does not pass rule 13 or rule 14 either.
- **The floor is file-only.** `PUT /v1/policies/{id}` refuses `when_no_grant` with a `400`, whatever its value, because the store reads a policy with a decoder that drops what it does not know, so a rollback would silently take a stored floor away. `grant_tool` may be written through it, which is how a hold ends on a running box with no restart.
- **Queue dedup and cap, for holds of the floor.** One agent, run and call in one org is one pending approval, and the answer names it, under a partial unique index and `ON CONFLICT DO NOTHING`. Past `WARDRYX_PENDING_PER_AGENT` pending approvals of the agent in that org the verdict and the reason are the same, the answer has no `approval_id`, the decision is recorded with `queue_full`, no row is added, and `approval_queue_full` fires once per agent per process. An answered row frees its place. Holds of other kinds are written as they always were.
- **`policy_loaded`**, a new event written once at start with the `policy_version`, the counts and the names of the floors, so an edit of the file leaves a trace. Replay counts it as no decision.
- **The candidate report.** `wardryx replay -policy <candidate>` lists, per agent and tool, what the candidate's floor would hold, every tool of a call and not only the first. **`-format json`** prints the run for a program, with `would_hold` beside `unexamined`.
- **`wardryx check`** adds a `TOOL CALLS` column, and `tool_calls` in its JSON, when a floor matches: which tools are granted, and that any other is held. With no floor it prints what it printed.

## Changed

- **A decision under either field is never `cacheable`, a model call included.** An enforcement point's cache has no call digest in its key, so an allow a token earned would open the tool with other arguments.
- **A floor's target runs across a line break.** A `*` compiles to `.*`, and `.` stops at a line break, so an agent id with one in it would walk past a floor on `*`. Every other policy keeps the glob it had.
- **Hold reasons of the floor quote and bound what the caller wrote.** The floor, the tool and the agent are formatted with `%q`, each cut to 200 bytes, because an agent id is unchecked past "not empty" and a reason reaches a console. An id with no `agent://` scheme is told that no grant can name it.
- **Reason sentences are held word for word.** Replay compares the reason, so a golden test now holds every sentence `Decide` writes. None of them changed.
- **The unanswered-approval sweep reads pending rows only**, through a new `ListPendingApprovals`, so the cost of a tick follows what is waiting and not everything ever decided.
- **The stale comment on single use is fixed.** The package comment of `internal/approval` still said a token is reusable for its TTL by default. It has been single-use by default since 1.0, and the comment now says so. Behaviour does not change.

## Limits

- The enforcement point is believed about whether a call exists, so a tool an agent reaches around the broker is not seen.
- An agent with a rule of its own and no grant is held.
- With a floor over an agent, each of its decisions reaches wardryx: a decision cache in front of it stores none of them.
- Under a static key the agent id is the caller's word, so a grant should carry `require_identity_source: [agent-token]`.
- An id with no `agent://` scheme cannot be granted, and only a person can let its calls through, one at a time.
- A call marked `arguments_truncated` binds only name, target and the flag, so leave single-use on.
- A grant returns its token once, to whoever decided. Whatever answers for a person has to hand it on to the enforcement point, or the hold ends only by writing a grant.
- On Postgres the limit is read in the statement that writes, so a burst can pass it by as many statements as run at that moment, at most 16 per instance. The key is exact. Rows of other holds count toward the limit, and a hold another rule reached first is written as it always was, so a queue fed by those is not bounded here.
- A candidate is the file given: a grant written through the API is not in it unless it is copied there, which errs toward reporting more.
