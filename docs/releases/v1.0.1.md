# Wardryx 1.0.1

One fix, no wire change: `wardryx replay` no longer reports a hold on a
spent approval token as the record and the code disagreeing about the past.

## The defect (wardryx#57)

Found by UPG-2 of the 1.0 proving run, a 0.1.0 store upgraded in place to
1.0.0. Under the 1.0 default a token allows once; its second presentation
records a hold whose reason is `approval_token was already redeemed once
under WARDRYX_APPROVAL_SINGLE_USE; a new approval is required`. The token is
never recorded (invariant 15: a live credential), so replay answers the plain
hold with the threshold's own reason, and 1.0.0 filed the row under
`diverged`, with the banner that nothing below it is trustworthy. Every
single-use refusal an operator's fleet recorded would have shown up that way.

## The fix

- A sixth row, `approval-spent`, beside `approval-decided`: the PDP held this
  again because the approval a human gave had already been used once. Same
  hold as replay reaches, a reason only the unrecorded token explains; the
  row is replayable and the counterfactual is measured against the hold.
- The sentence is a shared constant now, `pdp.ReasonApprovalSpent`, written
  by the decision handler and read back by replay, and the row is excused by
  that exact sentence and no other: a hold with any other reason the replay
  does not reproduce is still a divergence.
- Invariant 18 in CLAUDE.md names the fifth row; three tests, each red first
  against 1.0.0's replay; the third drives the real handler, its real event
  file and the real replay, so the two packages cannot drift apart silently.

## Compatibility

Additive: a new row in the replay report, which `compat/1.0.json` lists as
experimental; nothing on the wire, in the routes, in the policy fields or in
the event types moves. A 1.0.0 deployment moves to 1.0.1 by moving the image
tag; nothing to migrate.
